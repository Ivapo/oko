### Round 2 — Phase 2 only — 2026-08-14 — same reviewer (resumed) — **NOT READY**

Round 1's blocker resolved. One new blocker — **introduced by the fix for it**, which is
the failure mode `loops/review-spec.md` §3 warns about, and it was found because the
re-review prompt pointed the reviewer at that fix as the likeliest place to look.

**New blocker — check 3 required the tab column to update live after a drag, and nothing
in scope made a drag an event Oko sees.** Reordering a tab creates no session, terminates
none and changes no session variable, so an implementation built exactly to scope bullet 3
would have had a permanently stale tab column — and the setup forbids the restart that
would have hidden it. Worse, a check-3 failure would then have had two indistinguishable
causes, `tabs[]` not being display-ordered or Oko never refreshing, which destroys the
discriminating power check 3 was added for.

Both halves verified in `proto/api.proto` before the fix: `LayoutChangedNotification`
carries a whole `ListSessionsResponse`, so the new tab order arrives inline;
`NewSessionNotification` carries a `session_id` and nothing else, so it cannot place a
session at all. Scope bullet 3 now names **two** subscriptions with a division of labour,
and the payload asymmetry went into `rules/iterm-api.md` — a spec may drift, a rule may
not.

Non-blocking, all accepted: an escalation branch on check 3, in the shape Phase 1's check
1 uses, for the case where no source matches the tab bar; §2.4's identity claim narrowed
from "all eleven sessions" to what the probe actually prints, which is four sessions and
one never-fired assertion; and check 5's "close a third tab" excluded from the `nvim` tab
and Oko's own, which checks 6 and 7 still need. The reviewer also flagged that §2.8's
negative claim about tab scope rested on iTerm2's documentation while `tabIndex` and
`tabNumber` strings exist in the binary — checked, and every one is an Objective-C
selector or ivar, so the claim stands and now says so.

### Round 1 — Phase 2 only — 2026-08-14 — fresh reviewer, repo access — **NOT READY**

**Round 0 (asked once for this episode) — is this the right thing to build at all?** Yes.
Phase 2 produces the observable §1 names, minus only the status column, and is the first
phase a human can use. Phase 1's round-0 caveat still stands and is still not
disqualifying: the table overlaps what iTerm2's tab bar already shows, and Phase 3's
status column is the reason the tool exists — but Phase 2 is the frame that column hangs

One blocking finding, eleven non-blocking, all twelve accepted. This was the first round
with real code to check against, and the reviewer used it: every verb in scope bullet 1
was confirmed present in Phase 1's client, and the 5-row gate arithmetic re-derived.

**Blocker — the `tab` column had no established source, and gate check 1 could not tell a
right answer from a wrong one.** Check 1 tested only that the two split rows *share* a
number, which every candidate source satisfies. Establishing the source killed two of the
three: iTerm2's tab scope exposes no index at all, and the `t` component of `termid` is a
monotonic id rather than a position — Phase 1's own output shows `t0 t1 t2 t3 t4 t5 t8`
across seven tabs of one window, already three off the tab bar. §2.8 now names 1-based
position in `windows[].tabs[]` as the only remaining source, writes down the one property
nobody has established — that `tabs[]` is display-ordered — and pushes it into a new gate
check that compares the column against iTerm2's tab bar after a tab is dragged.

The gate went from four checks to seven and gained a second window, restoring the argument
Phase 1's gate makes and Phase 2 had dropped: with one window, "scoped to my own window"
and "listed everything" are the same output, so an implementation ignoring window scoping
passed everything. Also folded in: the split now happens while Oko is running and Oko is
restarted for no check; check 5 exercises `path` and `jobName` together and records the
stopwatch, since the 2 s literal rested on a `jobName` measurement while the check
exercised `path`; check 7 covers selection integrity, because closing a row above the
selection can silently re-point Enter at a different session — the wrong jump §2.7 argues
is worse than no answer. Check 4 stopped saying "the basename of the deepest foreground
process" and now says `jobName`, which differs for any name over 16 bytes.

Scope gained: what Phase 1 proved was the protocol and not the shape — its client is
blocking and one-shot, `Client::call` discards frames whose id does not match, and it never
issued a request after subscribing, so the interleaving Phase 2 needs has never run.
Close-out gained: re-pointing `rules/iterm-api.md`'s `sources` at `src/iterm/` so the next
`/sync-rules` does not regenerate the API rule from a throwaway spike, the fate of
`src/bin/probe.rs`, and user-facing documentation under §6's write-it-or-log-the-gap —
Phase 2 being the first phase a human can run, with no README in the repo.

**OQ-3 resolved in this round rather than at implementation time** — subscribe, no polling.
Phase 1 measured both branches, so leaving it open would have handed a settled question to
whoever wrote the plan; Phase 3's scope already says the same thing in its own words.

One partial rejection: the reviewer wanted `jobName`'s 16-byte truncation noted in §2.2.
Declined there — §2.2 makes no claim about truncation and OQ-2 already carries a dated
correction recording the limit — and handled where Phase 2 actually renders the value, in
the scope bullet and check 4.

### Round 2 — Phase 1 only — 2026-08-14 — same reviewer (resumed) — **NOT READY**

All five round-1 blockers confirmed resolved. One new blocker, which was the weakness the
author had flagged for testing in the round-2 prompt.

**New blocker — the mismatch branch of the identity check had no completion criterion,
and the checks above it presupposed the branch they allowed to fail.** The gate read "if
it prints a mismatch, that is a finding, not a failure … satisfied by having established
which" — but nothing defined *established*, no scope bullet produced an alternative key,
and the close-out's rules-file contents did not include one. Worse, checks 1–2 enumerated
"sessions in Oko's own window", and the only stated way to resolve that window was the
very UUID join the branch allowed to fail.

**Resolved by reordering the phase rather than patching the gate.** The probe now
establishes the join key *before* it enumerates anything; §2.1 carries an ordered fallback
list (UUID → tty device → `wNtMpK` prefix, the last noted as a position that expires when
a tab moves); check 1 passes on any candidate joining, with which one it was as the
deliverable, and fails only if none joins — an explicit escalation to a human, since
§2.4's status join and §2.5's navigation both rest on such a key existing.

Non-blocking, all accepted: a second iTerm2 window added to the gate setup, because with
one window "scoped to my own window" and "listed everything" produce identical output; the
probe's own line now accepts `zsh` **or** the probe binary name, since iTerm2 refreshes its
process cache on a poll and that was the one literal that could fail a *correct*
implementation; `rules/iterm-api.md` must document how to revoke or reset an authorization
grant, or a second person's first failure is unattributable; OQ-1 given an ordered
selection criterion and an escalation if no transport reaches the API; and §2.2 corrected
from "reports `node`" to "reports **a descendant of** `claude`" — `node` here only because
this machine's session runs an MCP subtree, `claude` on a session with no MCP servers —
which is the point that makes the process name configuration-dependent and therefore
unusable as an identity test.

### Round 1 — Phase 1 only — 2026-08-14 — fresh reviewer, repo access — **NOT READY**

**Round 0 (asked once for this episode) — is this the right thing to build at all?**
Yes, with a caveat recorded rather than waved past. The phase then under review produced
the observable in structurally complete form and the observable itself was the one settled
at adoption. The caveat: its *standing* value to a user is thin, because iTerm2's own tab
bar already shows roughly what a directory-and-process table shows, and the reason the tool
exists is the status column. What justifies the early phases is that they retire the risky
mechanisms — transport, liveness, activate-by-session-id — before hook work is built on
them. That argument is what the round-1 findings then reshaped into a separate spike phase.

Five blocking findings, all accepted, each verified independently by the author before
folding in:

1. **§2.1 named the wrong socket.** `iterm2-daemon-1.socket` is iTerm2's session-restoration
   multiserver — held by `iTermServer-3.6.11`, pid 1254 — not the scripting API endpoint,
   which is a separate WebSocket server inside iTerm2. A spike keyed to that path would have
   reverse-engineered the wrong protocol. §2.1 now states only where the endpoint is *not*
   and makes discovery a phase deliverable.
2. **The API is disabled and requires an authorization handshake nothing covered.**
   `EnableAPIServer` and `NoSyncEnableAPIServer` both absent from `com.googlecode.iterm2`;
   no listening TCP socket. §2.2's "no setup, no cooperation from the shell, nothing
   installed per-tab" was false as a description of what it takes to get a plain-tab row —
   narrowed to claim only no *per-tab* install, with enablement and per-process
   authorization moved into scope.
3. **The phase was not one plan-mode pass**, and the spec placed the OQ-1 spike in three
   incompatible places at once ("settled by a spike in Phase 1 planning", "answered before
   Phase 1 is planned", and inside the phase's own first scope bullet). **Resolved by
   splitting the phases:** Phase 1 became the transport spike alone, the table moved to
   Phase 2, and the hooks moved from Phase 2 to Phase 3. Nothing had shipped and no
   `reviewed` date existed, so no record was rewritten by the renumbering.
4. **Row identity was undefined — tab or session?** §1 and the gate said tab, §2.1 said
   session, and the identity and navigation mechanisms both key on panes. Settled as a
   recorded decision (§2.8): **one row per session**, `tab` column showing the tab index,
   two sessions in a split tab sharing an index. Phase 2's gate now splits a tab, because a
   gate with no split would pass either implementation.
5. **The gate was keyed to a method that does not reproduce its own literals.** macOS
   `ps -o comm=` prints a full path (measured: `/bin/zsh`, `/sbin/launchd`), and "that tab's
   foreground process" is not unique — iTerm2 reports the *deepest* job in the foreground
   group. Both gates now say **basename** and deliberately use tabs with no child process
   tree.

Non-blocking, all accepted: Oko's own row added to §1's sketch with counts reconciled
against the gate; the sketch's `claude` labels marked as end-state from the status file;
OQ-3 pinned to a ≤1 s poll interval against the 2 s gate; `cargo init` and concrete module
paths named; Rust/ratatui recorded as a decision (§2.9) with OQ-1's stakes corrected from
"decides whether the tech stack survives" to a transport question; `it2getvar` named and
rejected as a table transport while kept as the cheap way to learn Oko's own session id;
and the `TERM_SESSION_ID`-UUID-equals-API-session-id assumption flagged as unverified and
load-bearing.

**Correction to the author's own text, recorded because the spec asserted it:** OQ-2 had
called `caffeinate -i claude` a wrapper around the agent. It is a **child** — pid 99094,
ppid 99093, same process group. OQ-2 was rewritten around the deepest-foreground-job rule,
which is the larger and different hazard.

Nothing was rejected in any round.

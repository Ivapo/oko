    1  //! Rows, and how they stay true.                                                                                
    2  //!                                                                                                              
    3  //! One row per session (§2.8), scoped to the window Oko itself is in, ordered by tab index                      
    4  //! then position within the tab. The rows track reality by **subscription, not polling**                        
    5  //! (OQ-3), and it takes three kinds:                                                                            
    6  //!                                                                                                              
    7  //! - `NOTIFY_ON_VARIABLE_CHANGE`, per session *and* per variable, for `path` and `jobName`.                     
    8  //!   A session that appears later is covered only if it is subscribed on arrival.                               
    9  //! - `NOTIFY_ON_LAYOUT_CHANGE` for the shape of the window. Dragging a tab creates no                           
   10  //!   session, terminates none and changes no session variable, so this is the only event                        
   11  //!   that makes the `tab` column live — and its payload is a whole `ListSessionsResponse`,                      
   12  //!   so the new shape arrives inside the notification.                                                          
   13  //! - `NOTIFY_ON_NEW_SESSION`, because the two above do not cover a tab **opening**. Measured                    
   14  //!   rather than inferred: opening fires this and no layout change, closing fires the layout                    
   15  //!   change and not this. It carries an id and nothing else, so the list is fetched.                            
   16  //!                                                                                                              
   17  //! The status column has no subscription to hang on, because it comes from a directory of                       
   18  //! files rather than from iTerm2. It rides the tick this loop already wakes on: one `stat`                      
   19  //! of `~/.oko/status`, a re-read only when the mtime moved, and one comparison of the                           
   20  //! merged view — which is also the only thing that can notice a `working` going stale, since                    
   21  //! ageing writes no file and fires nothing.
